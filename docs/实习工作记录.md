### 001｜主工作流消息协议兼容修复

**改动时间：** 2026-07-15 16:42（纳入本记录的时间）  
**所属阶段：** 基线跑通 / 执行稳定性

#### 改进前的效果

1. Publisher 把下一执行节点写成自然语言 `Next step is delegating to...`，但后续逻辑依赖机器可读的 `{"next":"agent"}` 协议，模型可能无法稳定判断已执行节点并重复派发。
2. AgentProxy 将 Python `dict` 直接写入 LangChain 消息 `content`，与当前消息类型约束不兼容，可能在 Pydantic 校验时失败。

#### 实现内容

- Publisher 统一用 JSON 字符串保存下一 Agent：`{"next": "agent_name"}`。
- AgentProxy 使用 `json.dumps(..., ensure_ascii=False, default=str)` 序列化结构化执行结果。

#### 改进后的效果

- Publisher 状态从“供人阅读的自然语言”改为“可确定解析的 JSON 协议”。
- AgentProxy 输出从不兼容的字典对象改为 LangChain 接受的字符串，同时保留结构化内容。

#### 量化变化

| 指标 | 改进前 | 改进后 | 提升 |
|---|---:|---:|---:|
| Publisher 下一节点记录的机器可解析率（结构性） | 非强约束 | JSON 强约束 | 协议字段覆盖 0 → 1 |
| AgentProxy `content` 类型兼容路径 | `dict` | `str` | 消除 1 个确定的类型冲突点 |

> 运行时重复派发率和任务成功率需要用固定案例回归后补充，当前不虚构百分比。

### 003｜主 Agent 精准路由第一版

**改动时间：** 2026-07-15 17:06  
**所属阶段：** 改进方案 P1——主 Agent 精准路由

#### 改进前的效果

1. 用户自然语言直接交给 Planner；任务理解、Agent 选择和步骤编排耦合在一个 Prompt 中。
2. Agent 主要依靠名称和长文本描述，没有统一的能力、意图、动作、数据范围和风险边界。
3. 没有独立 `RoutingDecision`，页面无法说明“为什么选它、还有哪些候选、谁被权限排除”。
4. 页面手动选择 `coor_agents` 时，可绕过演示用户的前置可用 Agent 列表；细粒度检查只能等执行到 AgentProxy 才发生。
5. 中文任务场景规则存在乱码关键词。“怎么学习 Java”曾被 Planner 选给 researcher，随后因场景错配被 S-ABAC 拒绝。
6. Planner 能看到超出最终合法候选范围的 Agent 描述，候选边界主要依赖 Prompt 自觉遵守。

#### 实现内容

1. **建立三类标准契约**
   - `TaskProfile`：意图、任务类型、动作、实体、数据范围、场景标签、期望能力、风险、缺失字段和置信度。
   - `AgentCard`：部门、能力、意图、支持动作、数据范围、风险上限、Grant、工具、版本和状态。
   - `RoutingDecision`：Top-K 候选、分数明细、最终决策、置信度、reason code、排除项和 trace_id。
2. **主 Agent 统一入口**
   - 新增 `make_routing_decision`，形成“任务画像 → AgentCard → 权限边界 → 混合评分 → 置信度门”的固定链路。
3. **规则优先任务画像**
   - 覆盖 HR、编程学习、通信、会议、办公、差旅、风险、知识、文档、调研、天气等常用场景。
   - 明确规则命中时使用确定性结果；规则低置信度时才复用原 LLM 场景分析补充。
4. **权限感知候选路由**
   - 用户无权访问的 Agent 在 Planner 之前排除。
   - 手动选择 Agent 不再覆盖用户可访问列表。
   - Planner 只接收 Top-5 合法候选的能力描述；被排除 Agent 仅在审计页面展示，不把完整排除列表放进 Planner Prompt。
5. **混合评分和决策门**
   - 按方案实现：意图 35%、能力 25%、场景 15%、数据范围 10%、历史占位 10%、可用性 5%。
   - `>=0.80` 自动派发；`0.55~0.80` 要求澄清；`<0.55` 拒绝派发。
   - 缺少收件人等关键字段时直接进入 `CLARIFY`，Planner 不生成可执行步骤。
   - 复合任务允许不同 Agent 分别承担查询、生成等子动作，避免拿“最终动作”错误排除上游数据 Agent。
6. **接入现有 Planner 和工作流**
   - Planner Prompt 新增主 Agent 路由决策，只能在路由候选和 `TEAM_MEMBERS` 的交集中选 Agent。
   - 路由结果随 SSE 发送，并进入 Checkpoint 状态，便于执行和恢复时追踪。
7. **页面增加主 Agent 决策台**
   - 展示 TaskProfile、路由决策、置信度、候选得分、reason code、被排除 Agent 和排除原因。

#### 改进后的效果

- Planner 从“面对全部描述自由猜选”变为“在主 Agent 已完成权限过滤和评分后的合法 Top-K 中编排”。
- 路由行为形成标准对象，具备确定字段、reason code 和 trace_id，可以被日志、页面和后续评测直接复用。
- 歧义或字段缺失不再盲目派发；高置信任务自动派发，中低置信任务停止并解释。
- “怎么学习 Java”在规则画像中被识别为 `programming_learning`，期望能力为 Engineering/Learning；`coder` 的确定性结构评分为 0.95，避免再把它作为普通资料检索交给 researcher。
- “查询员工并生成报告”会同时保留 HR 与 Document 候选，支持主 Agent 后续做跨部门顺序编排。

#### 量化变化

| 指标 | 改进前 | 改进后 | 提升 |
|---|---:|---:|---:|
| 标准核心路由 Schema | 0 | 3 | 新增 TaskProfile/AgentCard/RoutingDecision |
| 独立主 Agent 路由阶段 | 0 | 1 | 从 Planner 中前移 1 个决策阶段 |
| Planner 可接收候选上限 | 全量可见 Agent | Top-5 合法候选 | 候选输入被硬限制 |
| 标准路由决策类型 | 0 | 3 | DISPATCH/CLARIFY/REJECT |
| 评分维度 | 0 | 6 | 意图、能力、场景、数据、历史、可用性 |
| 显式手选越权绕过点 | 1 | 0 | 消除 1 个前置授权绕过点 |
| 路由解释页面 | 0 | 1 | 新增主 Agent 决策台 |
| Java 学习 → coder 确定性评分（结构性） | 无独立评分 | 0.95 | 新增可解释 Top-1 结果 |

**待实测指标：**

- 用户无权 Agent 的路由前阻断率，目标 100%。

### 004｜Python 3.12 团队环境统一与完整执行链路修复

**改动时间：** 2026-07-17 08:55
**所属阶段：** 开发环境标准化与主 Agent 路由链路回归

#### 改进前的效果

1. 项目只声明 `Python >=3.12`，Python 3.14 也会被接受；实际运行出现 Pydantic V1 与 Python 3.14 不兼容警告。
2. 团队 `.env` 与本机 `.env` 的模型分配、MCP 开关和权限开关不一致，无法保证四位成员得到相同行为。
3. IDE/Windows 进程中的 `DEBUG=release` 会覆盖 `.env` 中的布尔配置，启动时出现非法布尔值告警。
4. 健康接口未读取 `USE_MCP_TOOLS`，MCP 实际关闭时仍显示“已启用”。
5. Windows Bash 工具只能转换整条命令开头的 `ls`，无法处理 `cd ... && ls`；子进程还会因 GBK/UTF-8 混用触发 `UnicodeDecodeError`。
6. Agent 执行失败被包装成普通成功消息，页面可能显示 `[ok]`，但消息内部实际是错误。
7. Production 阶段只向执行 Agent 发送“Confirm execution”，未明确注入原始问题和当前规划步骤，Agent 可能读取无关旧工作流自行猜测任务。
8. “怎么学习 Java”首次完整执行耗时 68.16 秒后触发 25 步递归上限，没有得到有效结果。

#### 实现内容

1. **锁定团队 Python 版本**
   - `requires-python` 从 `>=3.12` 收紧为 `>=3.12,<3.13`。
   - 新增 `.python-version`，固定使用 Python 3.12。
   - 使用 uv 0.11.29 重新生成锁文件，锁文件约束为 `==3.12.*`。
2. **统一模型和本地配置**
   - 规划、基础、视觉和远程 Agent 使用 `qwen3.5-27b`。
   - 代码任务使用 `deepseek-v4-flash`。
   - `.env.example` 形成不含密钥的团队模板；本地 `.env` 使用用户提供的真实配置且继续被 Git 忽略。
   - 浏览器、MCP 和 S-ABAC 默认按共享开发环境关闭。
3. **保证开发环境读取一致**
   - Development 环境以项目 `.env` 为准，避免 IDE/系统同名变量覆盖。
   - Production 环境仍保留平台注入环境变量的优先级。
4. **修正健康状态**
   - 健康接口接入 `USE_MCP_TOOLS`，关闭时返回 `enabled=false/status=disabled`。
5. **修复 Windows 工具执行**
   - 支持链式命令中 Unix 命令的转换，例如 `cd . && ls`。
   - 子进程切换 UTF-8 代码页并使用容错解码，消除中文路径读取线程异常。
6. **修复 Agent 失败传播**
   - Executor 返回失败时直接终止当前 AgentProxy，并交给工作流错误通道处理，不再伪装为正常消息。
7. **补齐执行上下文**
   - 每次 Agent 派发都显式注入原始用户问题、当前 Agent、分配步骤和 TaskProfile。
   - 编程学习咨询识别 `task_type=LEARNING + intent=programming_learning`，直接回答，不调用无关本地工具。
8. **降低非异常噪声**
   - 首次执行没有旧检查点、工作流尚未进入缓存等正常情况不再记录为 ERROR。
   - Windows 未安装 readline 时静默禁用命令历史，不再显示无意义初始化失败。

#### 改进后的效果

- 四位成员可以使用同一套 Python 3.12、模型名称和开关模板创建环境。
- 本机实际环境为 Python 3.12.10，核心依赖全部成功导入。
- `qwen3.5-27b` 与 `deepseek-v4-flash` 均完成真实 API 调用验证。
- Web、远程 Agent、远程工具和远程注册中心四个服务同时运行。
- Web readiness 为 Ready，模型已配置、Agent 数量为 17、搜索可用、MCP 正确显示关闭。
- “怎么学习 Java”完整执行能够正确路由至 `coder`、生成有效计划并返回相关学习指导。

### 005｜PowerShell 一键启动与关闭

**改动时间：** 2026-07-20  
**所属阶段：** 团队开发体验与运行稳定性

#### 改进前的效果

1. 完整 Demo 需要在多个终端中分别激活虚拟环境并启动 4 个服务，操作步骤较多。
2. 新终端容易误用 Anaconda 的 Python，导致 FastAPI 缺失或 Pydantic 版本冲突。
3. 用户复制终端提示符或报错文本后，PowerShell 会把这些内容当作命令解析。

#### 实现内容

- 新增 `start-superagent.ps1`，固定调用项目 `.venv`，在一个窗口中启动注册中心、远程工具、远程 Agent 和 Web 服务。
- 三个后台服务隐藏运行并将输出写入原有 `output` 日志目录。
- 启动前检查 8001、8010、8011、8012 端口，避免重复启动。
- 新增 `stop-superagent.ps1`，只关闭命令行属于当前项目的端口进程。

#### 改进后的效果

- 启动命令由 4 个终端、多次环境激活，简化为单窗口执行 1 个脚本。
- 启动过程不再依赖当前 PowerShell/Conda 环境，固定使用项目 Python 3.12 虚拟环境。
- 按 `Ctrl+C` 后自动清理本次启动的后台服务，也可单独执行关闭脚本兜底。
